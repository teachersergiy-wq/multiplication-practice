# API-контракт v1

**Статус: PLANNED.** Нічого з описаного нижче ще не реалізовано. VERIFIED лише те, що типи в `contracts/api.ts` проходять `tsc --strict`.

Типи й константи — у `contracts/api.ts`; цей файл описує правила. За розбіжності діє `contracts/api.ts`. Зміни контракту — лише через PR, який підтвердили виконавці фронтенду (Codex) і серверної частини (Grok).

## 1. Принципи

1. Браузер ніколи не визначає правильність, бал, завершення спроби чи статус публікації.
2. Ключі відповідей живуть лише в `private.assessment_answer_keys`. Їх пишуть і читають тільки серверні функції.
3. Читання виконує браузер напряму через `supabase-js` під RLS. Усе, що чіпає ключі, Auth-користувачів, підрахунок або зміну стану, — тільки через Edge Functions.
4. Роль викликача визначається за `profiles` у базі, ніколи за тілом запиту.
5. `service_role` існує лише в середовищі Edge Functions (Supabase підставляє його автоматично). У фронтенді, репозиторії, логах і повідомленнях його немає.

## 2. Що браузер робить напряму (під RLS), а що лише функції

| Роль | Напряму читає | Напряму пише | Лише через функції |
|---|---|---|---|
| Учитель | свої класи, учнів своїх класів (профіль містить логін, не пароль), предмети, свої шаблони й питання (без ключів), призначення, спроби й відповіді своїх класів | шаблони (створення як `draft`, редагування `draft`, видалення `draft`), `class_subjects`, призначення | створення/скидання/видалення учнів; питання й ключі; публікація; клонування; створення профілю |
| Учень | власний профіль і клас, призначення свого класу, метадані опублікованого шаблону (назва, режим, налаштування), власні спроби й відповіді | нічого | початок спроби, відповідь, завершення |

Учень **ніколи** не читає `assessment_questions` напряму: питання він отримує лише з `start-attempt`. Це закриває «підглядання» до початку спроби і дозволяє пізніше перемішувати питання для кожної спроби.

## 3. Конвенції функцій

- Виклик: `supabase.functions.invoke(name, { body })`, метод POST, JSON. Заголовок `Authorization: Bearer <access token>` додає клієнт. У всіх функцій `verify_jwt = true`.
- Відповідь завжди має вигляд `{ ok: true, data }` або `{ ok: false, error: { code, message, details? } }`. HTTP-статус береться з `HTTP_STATUS_BY_ERROR`.
- `message` — короткий англійський текст для логів. Інтерфейс показує власний український текст за `code`.
- Час — UTC ISO 8601; джерело часу — сервер. Клієнт коригує годинник за `serverNow`.
- Валідація: усі поля перевіряються на сервері за `LIMITS`. Невідомі поля відхиляються з `invalid_request`.
- Доступ до чужих об'єктів повертає `not_found`, а не `forbidden`, щоб не підтверджувати існування.
- CORS: дозволені джерела беруться зі змінної `ALLOWED_ORIGINS` (через кому). Символ `*` заборонений. Обробляється `OPTIONS`.
- Логи: ніколи не містять паролів, токенів, ключів відповідей і тіл відповідей учнів.
- Повторні запити: `submit-answer` ідемпотентний за парою (спроба, питання), `finish-attempt` повертає той самий результат. Створення учнів не ідемпотентне, тому інтерфейс блокує кнопку на час запиту.

| `code` | HTTP | Коли |
|---|---|---|
| `invalid_request` | 400 | не пройшла валідація |
| `unauthenticated` | 401 | немає чинного токена |
| `forbidden` | 403 | роль не дозволяє дію |
| `not_found` | 404 | об'єкта немає або він чужий |
| `conflict` | 409 | недопустимий стан (наприклад, тест уже опублікований) |
| `incomplete_assessment` | 409 | публікація неможлива; `details.questionIds` перелічує питання без валідного ключа |
| `assignment_not_open` / `assignment_closed` | 409 | поза вікном `opens_at`–`closes_at` |
| `retry_not_allowed` | 409 | `allow_retries = false`, спробу вже зроблено |
| `attempt_not_in_progress` | 409 | спроба вже завершена |
| `attempt_expired` | 409 | минув дедлайн |
| `already_answered` | 409 | на це питання вже відповідали |
| `rate_limited` | 429 | перевищено ліміт |
| `internal` | 500 | непередбачена помилка; без подробиць |

## 4. Облікові дані учнів (рішення D1, варіант B)

- Алфавіт: `abcdefghjkmnpqrstuvwxyz` (a–z без `i`, `l`, `o`).
- Логін: 3–4 літери; сервер завжди генерує 4. Унікальний у всій системі.
- Пароль: 2 літери + 4 цифри, наприклад `kd4817`. Це 23² × 10⁴ = 5 290 000 комбінацій (перевірено обчисленням).
- Вхід: `supabase.auth.signInWithPassword({ email: login + "@" + домен, password })`. Домен — конфігурація `STUDENT_EMAIL_DOMAIN` (на фронтенді `VITE_STUDENT_EMAIL_DOMAIN`), не секрет. Введення обрізається й переводиться в нижній регістр.
- Пароль видає лише система. Він повертається один раз у відповіді `create-students` / `reset-student-password`, не зберігається відкритим текстом і не логується.
- Лічильника невдалих спроб немає: захист тримається на довжині пароля й лімітах платформи (див. розділ 10, пункт 4). Це відома залишкова слабкість MVP.

## 5. Типи питань (рішення D2)

Спільне: у публічному рядку `prompt = { "text": ... }`; `choices` — масив (порожній, якщо варіантів немає). Ідентифікатори варіантів — непрозорі рядки, вони не кодують ні правильність, ні позицію. Оцінювання в MVP — «все або нічого» (`checker_version = 1`): правильна відповідь дає `points`, інакше 0.

| Тип | Що вводить учитель | Публічні дані для учня | Відповідь учня | Правильно, якщо |
|---|---|---|---|---|
| `true_false` | `correct: boolean` | без варіантів | `{ type, value }` | `value` збігається |
| `single_choice` | `options` (4–5), `correctIndex` | `choices` | `{ type, choiceId }` | обрано правильний варіант |
| `multiple_choice` | `options` (3–8), `correctIndexes` (≥ 1) | `choices` | `{ type, choiceIds }` | множина збігається повністю |
| `ordering` | `itemsInCorrectOrder` (3–8) | `choices` у **фіксованому перемішаному порядку** | `{ type, order }` | послідовність збігається повністю |
| `matching` | `pairs` (2–8) | `items` із `side`; права сторона перемішана | `{ type, pairs }` | усі пари збігаються, кожен лівий елемент має пару |
| `numeric` | `value`, `tolerance` (≥ 0, за замовчуванням 0) | без варіантів | `{ type, text }` | розібране число відрізняється від ключа не більше ніж на `tolerance` |
| `short_answer` | `accepted` (1–10), `caseSensitive` | без варіантів | `{ type, text }` | нормалізований текст збігається з однією з допустимих відповідей |

Правила, що їх реалізує сервер:

- **Перемішування.** Для `ordering` сервер зберігає елементи в порядку, відмінному від правильного (відхиляє збереження або перемішує, якщо збігається). Для `matching` права сторона зберігається перемішаною. Учень, який читає `choices`, не може вивести ключ.
- **Числа.** `text` обрізається, кома замінюється на крапку, дозволено `^[+-]?\d+([.,]\d+)?$`. Порівняння з допуском `1e-9` понад `tolerance`.
- **Текст.** Нормалізація Unicode NFC, обрізання, згортання пробілів, зведення апострофів (`'`, `’`, `ʼ`, `` ` ``, `´`) до одного символу, перетворення в нижній регістр, якщо не `caseSensitive`. Довжина до 200 символів. Буквена відповідь — це `short_answer`.
- **Структура відповіді.** Тип відповіді має збігатися з типом питання, ідентифікатори — належати питанню, масиви — без дублікатів. Інакше `invalid_request`.
- **Модель оцінювання (рішення власника, 2026-10-24, варіант B).** Для `true_false`, `single_choice`, `numeric`, `short_answer` лишається «все або нічого». Для багатокомпонентних типів діє частковий бал (`checker_version = 2`), частка `f` від 0 до 1:
  - `multiple_choice`: `f = max(0, (k − w) / n)`, де `n` — кількість правильних варіантів, `k` — правильно вибрані, `w` — хибно вибрані;
  - `ordering`: `f` = частка елементів на правильній позиції;
  - `matching`: `f` = частка правильно з'єднаних пар.
  `awarded_points = round(points × f, 2)`. `is_correct = true` лише при `f = 1`; будь-яке питання з `f < 1` (включно з частково правильним і без відповіді) рахується як помилка для `maxErrors`. `percent = score / maxScore × 100`, `passed` за `passPercent`/`maxErrors` без змін. У режимі `graded` `is_correct` і `awarded_points` лишаються `NULL` до завершення (D5); у `practice` `feedback` містить `isCorrect` і `awardedPoints` (за часткової відповіді `isCorrect = false`, `awardedPoints` > 0). Завершені спроби не перераховуються: вони зберігають бали за правилом, чинним на момент завершення.

## 6. Функції

Усі функції мають форму `ім'я(request) → data` за `contracts/api.ts`. Нижче — лише правила понад типи.

**`provision-teacher`** (будь-який увійшов користувач без профілю). Створює профіль учителя, школу, клас і зв'язок у одній транзакції. Ідемпотентна: якщо профіль є, повертає наявні ідентифікатори з `created: false`. Дозволена лише акаунтам зі списку дозволених (див. 8, R6) — інакше `forbidden`. Якщо акаунт належить учню — `forbidden`.

**`create-students`** (учитель, клас під його керуванням). До 40 учнів за виклик, до 200 в класі. Для кожного: унікальний логін і пароль, Auth-користувач із підтвердженою поштою, профіль `student`, зв'язок з класом. Створення Auth-користувача — зовнішній виклик поза транзакцією бази, тож функція має **компенсацію**: якщо будь-який крок не вдався, вона видаляє вже створені Auth-користувачів і записи цього виклику та повертає `internal`. Частковий успіх клієнту не повертається. Це окремий тест Grok.

**`reset-student-password`**, **`delete-student`** (учитель, учень його класу). Видалення каскадом прибирає історію спроб учня; інтерфейс має запитати підтвердження.

**`get-assessment-draft`** (власник шаблону). Єдиний спосіб прочитати ключі: повертає `AuthoredQuestion` з правильними відповідями. Для `ordering` повертає `itemsInCorrectOrder`, відновлений із ключа.

**`upsert-question`** (власник, шаблон у `draft`). Валідує за типом, розкладає дані на публічний рядок і приватний ключ **в одній транзакції**. Нове питання додається в кінець; зміна порядку — лише `reorder-questions`. До 100 питань у шаблоні (1000 для пулу, розділ 7a).

**`delete-question`**, **`reorder-questions`** (власник, `draft`).

**`publish-assessment`** (власник, `draft`). Умови: є хоча б одне питання; у кожного є валідний ключ потрібного типу; `points` > 0; `settings` валідні. Інакше `incomplete_assessment`. Після публікації шаблон і питання незмінні (на рівні RLS і функцій). Клієнт не може змінити `status` напряму (рішення D3).

**`clone-assessment`** (власник). Створює новий `draft` із копією питань і ключів і назвою з позначкою «(копія)».

**`generate-multiplication-test`** (вчитель). Створює новий `draft` з N числових питань «a × b = ?» за конфігом `multiplication_level_configs` (рівень 1–5). Вхід: `subjectId` (предмет `mathematics`), `gradeLevel` 1–11, `levelNumber` 1–5, `mode`, необов'язкова `title`. Правила:
- Конфіг береться для `gradeLevel`; якщо рядка немає, береться найближчий нижчий клас; якщо немає й такого, помилка `not_found`. Фактичний клас повертається в `configGradeLevel`.
- Множники `a` і `b` — цілі в `[minFactor, maxFactor]`. Пари без повторів (a × b і b × a вважаються однією парою); якщо унікальних пар менше за `questionCount`, питань створюється стільки, скільки є унікальних пар, і це видно з `questionCount`. Випадковість серверна (`crypto.getRandomValues`).
- Кожне питання: тип `numeric`, `value = a·b`, `tolerance = 0`, `points = 1`, `timeLimitSeconds = secondsPerQuestion`; текст питання «a × b = ?».
- `settings`: `passPercent`, `maxErrors` з конфіга; `totalTimeSeconds` не задається.
- Шаблон і питання створюються в одній транзакції (все або нічого), власник — викликаний вчитель, `grade_level = gradeLevel`, `status = draft`. Публікує вчитель окремо через `publish-assessment`.
- Не більше 30 згенерованих чернеток на вчителя на добу (захист від спаму); перевищення — `conflict`.
- Помилки: `invalid_request`, `not_found` (предмет/конфіг), `conflict`.
Конфіги змінюються лише міграцією (не клієнтом вчителя); у базі є рядки для 3 класу (рівні 1–5); міграція G9 додає окремі рядки для 5–9 класів і оновлює рядки 3 класу (рішення власника 2026-10-25; значення в issue G9). Якщо унікальних пар менше за `questionCount`, до списку додаються квадрати 11×11 і 12×12; якщо й цього бракує, питань стільки, скільки є пар. Для класів без свого рядка (1–2, 4, 10–11) діє правило найближчого нижчого.

**Керування вчителями (роль `admin`; рішення власника 2026-10-26: додавання вчителів без SQL).** Адміністратор — користувач із рядка `private.admin_users`; перший рядок (власник) додає координатор разовим запитом, не клієнт і не міграція в репозиторії. Усі чотири функції: `verify_jwt=true`, виклик лише адміністратора (інакше `forbidden`, учителю-не-адміністратору теж), записи в `private.admin_audit` (дія, виконавець, ціль, час; без паролів і без повного email у логах).
- **`add-teacher`**: `email` (нижній регістр, валідний), `fullName` 1–120. Створює Auth-користувача з підтвердженою поштою та згенерованим паролем (`crypto.getRandomValues`, 12+ символів без двозначних `0/O/1/l/I`), додає email у `private.allowed_teachers`, створює профіль, школу й клас як `provision-teacher`. Пароль повертається **один раз** у `temporaryPassword`, ніде не зберігається й не логується. Якщо Auth-користувач з таким email уже є — `conflict`. Багатокрокова операція має компенсацію: при збої видаляє створеного Auth-користувача й рядки цього виклику (як `create-students`). Ліміт: не більше 20 нових вчителів за добу.
- **`list-teachers`**: усі вчителі зі списку дозволених і/або з профілем `teacher`; без паролів і ключів.
- **`reset-teacher-password`**: новий згенерований пароль, повертається один раз; не для власного облікового запису (щоб не заблокувати себе) — `invalid_request`.
- **`set-teacher-active`**: вимикає або вмикає Auth-обліковий запис (бан без видалення даних); не для адміністраторів і не для себе — `forbidden`/`invalid_request`. Вимкнений вчитель не може увійти; його тести, класи й історія лишаються.
- Вчитель змінює власний пароль у застосунку через `supabase.auth.updateUser({ password })` (окремої функції немає); інтерфейс має нагадати змінити тимчасовий пароль після першого входу.
- Адміністратор бачить меню «Вчителі» лише якщо `list-teachers` не повернув `forbidden`.

**`create-class`** (вчитель). Створює клас у школі вчителя з одним предметом і рівнем (`name` 1–80, унікальна в школі; `subjectId` — активний системний або власний предмет; `gradeLevel` 1–12; не більше 20 класів на вчителя). Помилки: `invalid_request`, `not_found` (предмет/профіль), `conflict` (назва вже є). Клас потрібен для призначення тестів: призначення дозволене лише класу з рядком `class_subjects` того ж предмета й рівня (PK `class_id + subject_id` — один клас має один рівень на предмет).

**`set-class-subject`** (власник класу). Додає предмет і рівень до наявного класу; для того самого рівня ідемпотентна (`created: false`). Зміна рівня наявного предмета заборонена (`conflict`), якщо в класі вже є призначення цього предмета.

**`start-attempt`**, **`submit-answer`**, **`finish-attempt`** — розділ 7.

## 7. Спроба: життєвий цикл і час

**`start-attempt`.** Учень належить до класу призначення; `opens_at` ≤ зараз < `closes_at`; шаблон `published`. Якщо `allow_retries = false` і вже є завершена чи покинута спроба — `retry_not_allowed`. Якщо є незавершена спроба з чинним дедлайном — продовжується (`resumed: true`, ті самі питання, `answeredQuestionIds`). Якщо дедлайн минув — спроба фіналізується як `abandoned` (рахується, використовує повтор), і створюється нова, якщо повтор дозволений. Одночасно в учня на призначення не більше однієї спроби `in_progress` (унікальний частковий індекс).

**Дедлайн.** `deadlineAt = startedAt + ліміт + 15 с`, де ліміт — `settings.totalTimeSeconds`, а якщо його немає — сума `timeLimitSeconds` усіх питань, якщо їх задано в усіх; інакше дедлайну немає (`null`).

**Обмеження MVP (PARTIAL).** Ліміт на окреме питання контролює лише клієнт. Сервер контролює дедлайн усієї спроби. Учень технічно може затриматися на одному питанні, якщо вкладеться в загальний час.

**`submit-answer`.** Спроба `in_progress`, до дедлайну (інакше `attempt_expired`, спроба фіналізується); питання належить шаблону спроби; на нього ще не відповідали (`already_answered`).
- `practice`: сервер одразу обчислює `is_correct`, `awarded_points`, записує їх і повертає `feedback`.
- `graded`: сервер зберігає відповідь, а `is_correct` і `awarded_points` лишає `NULL`. `feedback` не повертається (рішення D5). **Жодна таблиця, яку може читати учень, не розкриває правильність незавершеної `graded`-спроби.**

**`finish-attempt`.** Власник спроби. Ідемпотентна. Обчислює для всіх питань (без відповіді — 0), для `graded` дописує `is_correct`/`awarded_points`, виставляє `score`, `max_score`, `passed`, `elapsed_ms`, `finished_at`. `passed`: `null`, якщо не задано ні `passPercent`, ні `maxErrors`; інакше `true` лише коли виконано кожну задану умову (`percent ≥ passPercent`, `mistakes ≤ maxErrors`). Після дедлайну приймаються лише відповіді, що надійшли вчасно.

## 7a. BIG таблиця множення: пул питань (рішення власника 2026-10-26)

Окремий тест, у якому шаблон містить **банк** питань, а кожна спроба отримує **випадкову вибірку** з банку за рівнями складності. Учень може починати тест багаторазово (`allow_retries = true` у призначенні), і кожна нова спроба має новий випадковий набір.

**Модель.**
- `assessment_questions.difficulty smallint` (1–5, `NULL` для звичайних шаблонів). `AssessmentSettings.pool = { levelCounts: [n1..n5] }` позначає шаблон-пул; для нього **кожне** питання має `difficulty`. Приклад власника: 30 питань = `[5, 10, 10, 5, 0]`.
- Нова таблиця `assessment_attempt_questions(attempt_id, question_id, position)`: вибірка зберігається при старті спроби; `PRIMARY KEY (attempt_id, question_id)`; RLS: учень читає свої, учитель-власник читає спроби своїх призначень; запис лише service_role.
- Ліміт питань у шаблоні: 100 для звичайного, **1000 для пулу**.
- Публікація пулу (`publish-assessment`): кожне питання має `difficulty`, `Σ levelCounts` у 1–100, і для кожного рівня d у банку не менше `levelCounts[d-1]` питань (інакше `incomplete_assessment`).

**Поведінка спроби.**
- `start-attempt` для пулу: нова спроба — для кожного рівня d випадково (без повторів) вибирається рівно `levelCounts[d-1]` питань, порядок питань у спробі випадковий; вибірка записується в `assessment_attempt_questions` і повертається в `questions` (форма `PublicQuestion` незмінна; правильні відповіді не розкриваються). Продовження (`resumed: true`) повертає **ту саму** вибірку. Одночасні виклики не створюють дві вибірки для однієї спроби.
- `submit-answer`: питання має належати вибірці цієї спроби (інакше `not_found`).
- `finish-attempt`: `maxScore`, `questionCount`, `mistakes`, відсутні відповіді рахуються **лише по питаннях вибірки**. Дедлайн: `totalTimeSeconds`, а якщо його немає — сума `timeLimitSeconds` питань **вибірки** (за наявності в усіх).
- Результати вчителя (C9/C10) беруть перелік питань спроби з `assessment_attempt_questions`.
- Клон (`clone-assessment`) копіює банк і `difficulty`, `settings.pool`.

**`generate-multiplication-bank`** (вчитель). Створює чернетку-пул і банк за правилами нижче; відповідь — `bankSize`, `bankByLevel`. Транзакційно, ліміт з `generate-multiplication-test` (30 чернеток/добу разом). Питання `numeric`, `tolerance = 0`, текст «a × b = ?», «a ÷ b = ?», «a × b ÷ c = ?», «a ÷ b × c = ?».

**`bulk-update-questions`** (власник, `draft`): масово змінює `difficulty`, `points`, `timeLimitSeconds` або видаляє до 500 питань за виклик (рівно одне з `update`/`delete`); без зміни ключів відповідей. Для звичайних шаблонів `difficulty` не змінюється (`invalid_request`).

**Склад банку (n ∈ 0..10; порядок множників розрізняється: a × b і b × a — різні питання).**
- Множення: усі впорядковані пари `a × b`, `a, b ∈ 0..10` (121 питання). Складність (найнижча з підходящих): рівень 1 — один із множників 0, 1, 2 або 10; рівень 2 — один із множників 3 або 5, або `a = b` (n × n); рівень 3 — один із множників 4, 6, 7, 8, 9.
- Ділення: `a ÷ b = k`, `b ∈ 1..10`, `k ∈ 0..10`, `a = b·k` (110 питань; ділення на 0 немає). Рівень 1 — `a = 0` (0 ÷ n), `a = b` (n ÷ n), `b = 1` або `b = 10`; рівень 2 — `b = 2`; рівень 3 — `b ∈ {3, 4, 5}`; рівень 4 — `b ∈ {6, 7, 8, 9}`.
- Рівень 5: складені вирази `a × b ÷ c` і `a ÷ b × c` з операндами 2..10, усі проміжні й кінцеві результати цілі й у межах таблиці (кінцевий результат 2..10 для `a × b ÷ c`; `a = b·k`, `k, c ∈ 2..10` для `a ÷ b × c`); виключаються тривіальні (`c = a` або `c = b`); не більше 200 таких виразів, обраних випадково; плюс квадрати 11², 12², 13², 14², 15².
- Якщо питання підходить під кілька рівнів, система ставить **найнижчий**, а вчитель за потреби змінює рівень вручну (`bulk-update-questions`).
- Типові бали й час за рівнями (вчитель змінює перед публікацією): бали 1 / 1 / 2 / 3 / 4, час 8 / 8 / 10 / 12 / 20 секунд.
- Орієнтовний розмір банку ≈ 470 питань; точні `bankByLevel` повертає функція.

## 7b. Змагальні тести («Супер рівень») і рейтинги (рішення власника 2026-10-27)

**Статус: PLANNED (контракт). Реалізація — після окремого рішення власника; не входить у G11/C14.**

### Види тестів
- **Обов'язковий** — наявні шаблони й призначення (оцінювання, тренування, домашня робота). Не змінюється.
- **Змагальний** — окремий вид: учень **сам обирає** тему зі списку для свого класу; результат потрапляє в рейтинг лише за його згодою. Учитель нічого не призначає.

### Теми (`competitive_topics`, довідник)
`code`, `title`, `subject`, `grade_min`, `grade_max`, `generator` (ключ серверного генератора), `active`. Початкові: `multiplication_table` (3–11 кл., спершу множення, далі пари ділення), `rational_addition` (6–11), `chemical_elements` (7–11). Нову тему додає лише адміністратор через міграцію + генератор. Учень бачить теми, де `grade_min ≤ grade класу ≤ grade_max`.

### Правила забігу (run)
- Нескінченна послідовність питань, генерується **сервером по одному**; наступне питання не відомо клієнту наперед, ключ відповіді лишається в `private`.
- Забіг закінчується **першою помилкою** або **таймаутом** відповіді. Результат: `score` = кількість правильних відповідей поспіль, `durationMs` = час від першого питання до кінця.
- Ліміт часу на відповідь: старт 7,0 с, мінус 0,5 с кожні 5 правильних відповідей, **не менше 0,3 с** (рішення власника: «мінімальний час на відповідь — 0,3 с»). Тобто 0,3 с досягається після 70 відповідей і далі не змінюється.
- Ліміт рахує сервер від моменту видачі питання. Через мережу додається фіксований допуск `graceMs` (пропозиція 1000 мс, значення зберігається в налаштуванні теми, **ЗВІРИТИ на телефонах**); у відображенні таймера допуск не показується.
- Сервер перевіряє відповідь і одразу повертає наступне питання або завершення (одна відповідь = один запит).
- Для 3–11 кл. діапазон множників/складність визначає тема й рівень забігу (перший етап — таблиця множення в межах таблиці 0–10, далі ділення; точні набори — в специфікації генератора теми).

### Найкращий результат і спроби
На пару (учень, тема) зберігаються: `bestScore`, `bestDurationMs`, `bestAt`, `attemptCount`. Кращим вважається більший `score`, при рівності — менший `durationMs`. Кожен забіг зберігається окремо (дата-час початку й кінця, `score`, `durationMs`).

### Рейтинги
Області (`scope`): `class` (кращі в класі), `school` (у школі), `school_year` (у цьому навчальному році; рік = 1 вересня – 31 серпня за `finished_at`), `absolute` (усі класи за всі роки). Рейтинг будується з **кращого** результату кожного учня, лише з опублікованих.
- Участь за згодою. Після завершення забігу відповідь містить `qualified`: список областей, у **топ-10** яких (пропозиція N = 10) потрапив цей результат, з місцем. Учень обирає: **не публікувати** (за замовчуванням) або опублікувати як:
  - `nickname` — згенерований нікнейм (`profiles.generated_nickname`);
  - `anonymous` — «Учень» без імені;
  - `name` — ім'я та прізвище; **лише для області `class`**.
- У областях `school` і `absolute` ім'я ніколи не публікується: допустимі `nickname` і `anonymous`. Учень може змінити вид публікації або зняти публікацію (`unpublish`).
- Дані учнів — лише синтетичні в тестах; публічні рейтинги не містять `student_id`, логіна, класу в `absolute`/`school`.

### Що бачить учитель
Для власних класів: **ім'я**, кількість спроб (`attemptCount`), дату й час кожного забігу, тривалість забігу (`durationMs`), найкращий `score`. Це не залежить від публікації в рейтингу.

### Вимоги до бази (Grok, окремим завданням)

### Вимоги до інтерфейсу (Codex/Grok, окремим завданням)
Екран «Змагання» учня: теми, мій найкращий результат, кнопка старту, швидке введення (як у C14: фокус, Enter), візуальний таймер, екран завершення з повідомленням «Ти потрапив у ТОП-N: …» і вибором виду публікації; екран рейтингу з вкладками областей; екран учителя з таблицею (ім'я, спроби, дата-час, тривалість). Мобільний вигляд 360×640.

### Відкриті питання до власника
1. Чи розділяти рейтинг за класом навчання (паралель) у `school`/`absolute`, чи показувати всіх разом?
2. Топ-N = 10 і ліміт 200 забігів на добу — прийнятно?
3. `graceMs` = 1 с — прийнятно для 0,3 с на пізніх етапах? (потрібна перевірка на телефонах)
4. Етап ділення для `multiplication_table`: після скількох правильних відповідей переходити (пропозиція: після всіх 121 пар множення або після 60 відповідей)?

## 11. Вимоги безпеки (обов'язкові)

- Ключі відповідей, `service_role`, паролі й токени не потрапляють у відповіді, логи, репозиторій і повідомлення.
- Кожна нова таблиця має RLS, явні мінімальні grants і тест на `anon`, учня, вчителя A і вчителя B.
- Кожна функція перевіряє роль із бази й належність об'єкта.
- Жодна міграція не застосовується до production без рішення власника.
- У розробці й тестах лише синтетичні дані, без реальних даних учнів.

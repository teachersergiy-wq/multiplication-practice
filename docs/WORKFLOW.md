# Правила роботи над проєктом

Проєкт ведуть кілька виконавців. Ці правила потрібні, щоб вони не перетиналися, а стан завжди відповідав дійсності.

## Ролі й файли

| Роль | Хто | Файли |
|---|---|---|
| Власник | власник проєкту | рішення про злиття PR, застосування міграцій на production, секрети |
| Координатор | Claude | `docs/**`, `contracts/api.ts`, `contracts/tsconfig.json`, `.github/**`, Hub (`AI_CONTEXT_HUB`) |
| Фронтенд | Codex | `src/**`, `index.html`, `vite.config.ts`, `package.json`, `package-lock.json`, `.env.example` |
| Сервер | Grok | `supabase/**`, `contracts/database.types.ts` |

Один PR не змінює файли двох ролей. Якщо задача вимагає змін у чужих файлах, виконавець описує потрібну зміну в PR, а власник файлу вносить її окремо.

## Гілки й PR

- Власна гілка на кожну задачу: `codex/<назва>`, `grok/<назва>`, `claude/<назва>`.
- У `main` не пушать. Зливає лише власник; для чистої історії радимо **squash merge**.
- PR заповнює шаблон `.github/pull_request_template.md` і закінчується звітом передачі (PROJECT / CHANGED / VERIFIED / DECISIONS / TODO / FILES).

## Стани

Кожне твердження про стан має позначку:

- **VERIFIED** — запускалося, є команда й результат;
- **PARTIAL** — частково, вказано, що саме;
- **PLANNED** — ще не реалізовано;
- **BLOCKED** — не можна виконати, вказано причину.

Результат, який виконавець отримав у власному середовищі, пишуть як «виконавець повідомляє». Незалежне підтвердження дає CI на GitHub.

## Що перевіряє координатор у кожному PR

1. Змінено лише файли виконавця.
2. Відповідність `docs/API_CONTRACT.md` і `contracts/api.ts`.
3. Немає секретів, `service_role` у клієнті, реальних даних учнів.
4. Для кожної нової таблиці чи функції є RLS або мінімальні права й тести для anon, учня, вчителя A і вчителя B. Тест перевіряє те, що заявляє: негативні тести мають справді падати, коли захист зламано.
5. Ключі відповідей не виходять за межі `private` і серверних функцій.
6. Позначки VERIFIED / PARTIAL / BLOCKED чесні.
7. CI зелений.
8. Жодної міграції не застосовано до production.

Результат рев'ю: **затверджено**, **потрібні зміни** (з переліком) або **відхилено** (з причиною). Вирішує злиття власник.

## Міграції

- Файл міграції має версію, що збігається з версією, застосованою в проєкті. Застосовані міграції не змінюють: зміни — новим файлом із наступною версією.
- Права видаються явно й мінімально: після міграції `20261018010000` права за замовчуванням для `anon` і `authenticated` вимкнені, тому кожна нова таблиця потребує власних `GRANT`.
- Міграції перевіряють на локальному Supabase (CI) або на гілці Supabase за дозволом власника. На production їх застосовує лише власник.

## Дані й секрети

- У репозиторії, повідомленнях і логах немає паролів, ключів API, `service_role`, токенів, реальних даних учнів.
- У розробці й тестах — лише синтетичні дані.
- Публічні значення (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`) не є секретами, але лежать у `.env.local`, а не в репозиторії.

## Hub

Після суттєвих змін координатор оновлює `CURRENT_STATE`, `DECISIONS`, `TODO`, `CHANGELOG` у `AI_CONTEXT_HUB`, використовуючи лише перевірені факти. Виконавці описують результат у PR і не редагують Hub самостійно.
